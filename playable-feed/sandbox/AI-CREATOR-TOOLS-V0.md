# Playloop AI creator tools v0

Playloop should be easy for any capable AI to author against without exposing application internals or arbitrary execution. The AI-facing surface is a small set of typed operations over GameSpec drafts and reviewed assets.

This document is intentionally transport-neutral. The same operations can later be exposed through REST, an MCP server, a ChatGPT/Claude/Gemini connector, a local creator CLI, or an in-app assistant.

## Principle

The AI can **author data and request reviewed media**. It cannot upload/execute JavaScript, call player APIs, bypass moderation, sign its own package or choose arbitrary production URLs.

```text
AI
 │
 ├── create/edit GameSpec draft
 ├── request normalized asset
 ├── validate
 ├── simulate
 ├── inspect diagnostics
 ├── capture trusted preview
 └── submit for review
          │
          ▼
Playloop publishing service
          │
          ▼
public signed package
```

## Tool: `get_runtime_capabilities`

Returns the exact supported schema/runtime and budgets.

Example response:

```json
{
  "runtime": "playloop-2d-v0",
  "schemaVersion": 1,
  "maxSpecBytes": 16384,
  "maxDeclaredAssetBytes": 262144,
  "entityKinds": ["circle", "rect", "text", "sprite"],
  "events": ["start", "tick", "tap", "pointerDown", "pointerMove", "pointerUp", "timer", "collision", "entityExit"],
  "actions": ["setVar", "addVar", "setEntity", "moveEntity", "setVelocity", "spawn", "destroy", "emit", "sound", "haptic", "complete", "fail", "if"]
}
```

An AI should call this instead of assuming capabilities from training data.

## Tool: `create_game_draft`

Input:

```json
{
  "title": "Meteor Dodge",
  "prompt": "optional creator intent for audit/history",
  "gameSpec": { "...": "GameSpec v0" }
}
```

Output:

```json
{
  "draftId": "draft_123",
  "revision": 1,
  "validation": { "ok": true, "errors": [], "warnings": [] }
}
```

Draft creation never publishes.

## Tool: `update_game_draft`

Uses optimistic revision control so two AIs/browser tabs do not silently overwrite each other.

```json
{
  "draftId": "draft_123",
  "expectedRevision": 3,
  "gameSpec": { "...": "replacement GameSpec" }
}
```

For v0, replacement semantics are simpler and safer than arbitrary JSON Patch generated by a model. A later API can add bounded field-level operations if needed.

## Tool: `request_asset`

The AI describes or uploads draft media. The service returns only after normalization/moderation suitable for preview use.

Text-to-image example:

```json
{
  "draftId": "draft_123",
  "kind": "image",
  "source": {
    "type": "generate",
    "prompt": "tiny pixel-art orange meteor, transparent background, centered"
  },
  "target": {
    "maxWidth": 128,
    "maxHeight": 128,
    "preferAtlas": true
  }
}
```

Response:

```json
{
  "asset": {
    "id": "meteor",
    "kind": "image",
    "ref": "sha256:...",
    "bytes": 712,
    "mime": "image/webp",
    "width": 64,
    "height": 64
  },
  "review": {
    "status": "preview_allowed"
  }
}
```

The AI receives no raw CDN credential and cannot choose the public URL.

## Tool: `pack_sprite_atlas`

Optional host tool for making lightweight output easier for AIs.

Input:

```json
{
  "assetRefs": ["sha256:ship...", "sha256:meteor...", "sha256:coin..."],
  "padding": 0,
  "maxDimension": 512
}
```

Output:

```json
{
  "atlas": {
    "id": "atlas-1",
    "kind": "image",
    "ref": "sha256:atlas...",
    "bytes": 4096,
    "mime": "image/webp",
    "width": 192,
    "height": 64
  },
  "frames": {
    "ship": { "sourceX": 0, "sourceY": 0, "sourceWidth": 64, "sourceHeight": 64 },
    "meteor": { "sourceX": 64, "sourceY": 0, "sourceWidth": 64, "sourceHeight": 64 },
    "coin": { "sourceX": 128, "sourceY": 0, "sourceWidth": 64, "sourceHeight": 64 }
  }
}
```

This lets the platform optimize transport without asking the model to manipulate image bytes itself.

## Tool: `validate_game`

Runs schema, publication-policy and resource-budget validation.

```json
{
  "draftId": "draft_123",
  "revision": 4
}
```

Response should be diagnostic and machine-fixable:

```json
{
  "ok": false,
  "errors": [
    {
      "path": "templates.meteor.sourceWidth",
      "code": "ATLAS_FRAME_OUT_OF_BOUNDS",
      "message": "source rectangle exceeds asset dimensions",
      "limit": 128,
      "actual": 160
    }
  ],
  "warnings": []
}
```

The current JS validator returns human strings. A production authoring API should add stable error codes/paths while retaining readable messages.

## Tool: `simulate_game`

Runs trusted deterministic probes, never model-provided code.

Input:

```json
{
  "draftId": "draft_123",
  "seeds": [1, 7, 42],
  "maxSimulatedMs": 15000,
  "bot": "generic-pointer-v0"
}
```

Output includes:

- crashes;
- terminal runs;
- peak entities;
- peak interpreted operations;
- semantic events/effects;
- optional trace references;
- warnings when generic probes cannot establish beatability.

A simulation pass means **safe enough for this automated probe**, not "fun" or guaranteed beatable.

## Tool: `capture_preview`

The service runs the reviewed GameSpec in a trusted renderer and returns a still/short clip reference. The AI cannot supply executable preview HTML.

Possible inputs:

```json
{
  "draftId": "draft_123",
  "seed": 42,
  "mode": "6s_autoplay"
}
```

The preview can become the passive part of a video+playable social post later.

## Tool: `submit_for_review`

```json
{
  "draftId": "draft_123",
  "revision": 7,
  "creatorDeclaration": {
    "ownsOrCanUseAssets": true
  }
}
```

The server freezes/canonicalizes that revision, reruns validation, asset/media review and automated simulations, then either rejects with diagnostics or creates a publication candidate.

The AI cannot call `publish_public` directly in v0.

## Tool: `remix_game`

Remix should create a new draft with provenance, not mutate the source game.

```json
{
  "sourceGameId": "game_abc",
  "title": "Meteor Dodge but everything is frogs"
}
```

Output records source/version attribution and returns an editable draft.

This is important for the social loop:

```text
watch creator post
  -> play
  -> remix with AI
  -> publish variant
  -> share challenge/clip
```

## Creator-owned social actions remain outside the game

AI tools may eventually help draft a caption or configure a challenge, but the GameSpec sandbox never gets operations such as:

- send_tip;
- follow_user;
- post_comment;
- DM_user;
- read_private_profile;
- access payment credentials.

Those are explicit shell/backend user actions with their own permissions.

## Resource-aware generation guidance

The AI should optimize in this order:

1. use primitives when visuals do not matter;
2. reuse already-approved creator/system assets;
3. pack related sprites into an atlas;
4. avoid unused assets;
5. keep only referenced game assets in the package;
6. prefer short normalized audio cues;
7. stay inside instant-tier byte and decoded-memory budgets.

A future `validate_game` response should expose cold bytes and likely cached bytes so the model can optimize toward actual user transfer cost.

## Plugin/MCP implementation

A Playloop MCP server can expose the operations above almost directly. The server should return the GameSpec JSON Schema and runtime reference as resources, while tools perform draft/review actions.

The important security property is that connecting an AI grants access to **creator drafts**, not to the player runtime or arbitrary backend/database APIs.

## v0 validation experiment

Before building a full creator UI, use this contract manually with several different AIs:

1. give the AI the schema and tool descriptions;
2. ask for 20 materially different game concepts;
3. have it produce/repair GameSpecs without Playloop source access;
4. normalize a small set of generated assets;
5. run automated review;
6. judge whether the resulting games differ mechanically and visually enough to justify deeper platform work.

The key signal is not whether an AI can emit valid JSON once. It is whether the constrained language remains expressive enough that creators do not immediately feel the sandbox underneath every game.
