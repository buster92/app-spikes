## UX findings from the phone test

### Bus Jam

The first Bus Jam version was conceptually unclear even to a player who already knew the intended genre. A large colored rectangle at the top did not read immediately as a bus, and colored dots did not read immediately as passengers.

The reference mechanic is closer to a directional escape puzzle:

- mixed colored buses occupy a board
- every bus points toward its exit direction
- buses can leave only when their path is clear
- a passenger line at the top shows color demand, front passenger first
- a limited parking area temporarily holds buses whose color does not match the current passenger

Round 3 replaces the first abstraction with this directional-board model and logs blocked taps, bus exits, direct boarding, parking, parking overflow, and completion/failure.

A later playtest exposed a second comprehension issue: when a matching bus and the front passenger disappeared at the same time, the correct action looked like a rendering bug. The next pass makes causality explicit with a short boarding beat: the passenger visibly moves toward the matching bus, the status explains the match, and only then does the bus depart. Parked buses use the same visible boarding feedback when they satisfy the next passenger.

### Match-3 vs feed navigation

An upward tile swipe inside Micro Match could be captured by the parent feed as “next game”, causing an accidental irreversible skip.

Round 3 marks Match-3 as a game-owned swipe surface and guards the parent feed listener so game swipes win while the round is active. This fixes the concrete failure without globally disabling feed swiping.

A generic one-step feed-back/undo remains a possible later UX feature, but it is not required to solve this specific gesture conflict and would add previous-round state/analytics semantics to the spike.

### Likes

Add a lightweight per-mechanic Like control to the post-game result state, not on top of the live game. This avoids competing with game input while providing an explicit preference signal. Likes persist locally and are exported with the behavior log.

### Reward visibility

The telemetry proves progression events were occurring, but the player reported not perceiving level-ups or record hits. That means the problem was reinforcement visibility, not missing progression data.

Round 3 adds a larger queued reward burst for:

- level-up events
- first personal-record crossings
- streak milestones (3, 5, 10, then every 5)

The reward surface is deliberately stronger early in the experience while still staying short enough not to interrupt `play → swipe → play`.

### Session fatigue

The games remain fun, but the feed is almost entirely active/high-attention content. Reaction, memory, timing and puzzle rounds demand continuous input. After roughly 15 minutes, play can become tiring even when the individual games are still enjoyable.

This is a product-level constraint rather than a single-game tuning problem. Infinite active microgames do not necessarily produce long comfortable sessions. A future experiment should test a lower-effort discovery layer such as autoplay/ghost previews, watching another run, or creator/challenge cards that can be consumed passively before choosing to play.

### Creator / social-network hypothesis

A promising longer-term direction is to make the playable object itself the social post: creators describe a microgame to AI, preview it, publish it, and other users can watch, play, like, challenge or remix it.

The first implementation should not allow AI-generated arbitrary JavaScript. A small declarative GameSpec over supported mechanics is safer, more measurable, and easier to moderate. See `CREATOR-NETWORK-HYPOTHESIS.md` for the proposed validation path.

## Validation focus after this pass

1. Is the directional Bus Jam understandable without explanation, including the new boarding/departure feedback?
2. Can the player swipe tiles upward in Match-3 without leaving the game?
3. Does the Like control get used naturally after a round?
4. Are level/record/streak reinforcements actually noticed?
5. Does reinforcement increase continuation without making the feed feel noisy?
6. Does a future low-effort preview mode extend sessions without increasing fatigue?
